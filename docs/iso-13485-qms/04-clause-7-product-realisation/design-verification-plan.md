## 1. Purpose
This document outlines the Design Verification Plan for the Naomi AI-powered chatbot, in accordance with ISO 13485:2016 (clause 7.3.6). The purpose of verification is to provide objective evidence that the software design outputs (code, architecture, configurations) meet all specified design inputs (functional, safety, and performance requirements).

## 2. Verification Methods
Verification of the Naomi system is achieved through a combination of automated and manual methods:
*   **Automated Unit and Integration Testing:** Executed via Vitest to verify module-level logic and inter-module communication.
*   **Static Code Analysis:** Automated scanning of TypeScript code for syntax, style, and known vulnerabilities during the CI/CD pipeline.
*   **Security Scanning:** Automated dependency checking and container/worker configuration scanning.
*   **Code Review:** Mandatory peer review of all code changes via GitHub Pull Requests.

## 3. Specific Verification Activities
The following critical activities will be conducted to verify system behaviour against safety and functional requirements:

*   **VA-01: Triage Classification Accuracy Testing:**
    *   *Method:* Automated testing of the triage classifier against a dataset of 500 annotated paediatric queries.
    *   *Acceptance Criteria:* >95% accuracy in correctly categorising severity (Routine, Urgent, Emergency).
*   **VA-02: Escalation Trigger Testing:**
    *   *Method:* Unit tests forcing specific "red flag" inputs to verify the escalation module bypasses generation.
    *   *Acceptance Criteria:* 100% of defined "red flag" scenarios trigger the correct NHS 111/999 escalation response.
*   **VA-03: Prompt Injection Testing:**
    *   *Method:* Execution of a dedicated adversarial testing suite attempting to override system prompts.
    *   *Acceptance Criteria:* Zero successful prompt injections that cause the system to ignore its safety constraints or reveal system prompts.
*   **VA-04: Rate Limiter Testing:**
    *   *Method:* Integration testing simulating high-volume requests from a single IP.
    *   *Acceptance Criteria:* Requests exceeding the defined threshold (e.g., 20 per minute) are successfully blocked with a 429 status code.
*   **VA-05: Retrieval Relevance Testing:**
    *   *Method:* Testing the Vectorize RAG pipeline against standard queries.
    *   *Acceptance Criteria:* The top 3 retrieved chunks must contain clinically relevant information for the test query in >90% of cases.
*   **VA-06: Generation Safety Rule Testing:**
    *   *Method:* Automated testing using `test-scenarios-runner.ts` evaluating generated text against the "never diagnose" and "never prescribe" rules.
    *   *Acceptance Criteria:* Zero violations of safety rules across the test dataset.

## 4. Verification Environment
Verification activities are conducted in two environments:
*   **Local Development Environment:** Developers run unit tests locally via Wrangler and Vitest before pushing code.
*   **CI/CD Pipeline (GitHub Actions):** The definitive verification environment. All tests, static analysis, and builds run in a clean, reproducible Ubuntu-based runner environment upon every commit to a pull request.

## 5. Responsibilities
*   **Software Engineers:** Responsible for writing and maintaining automated tests.
*   **Quality Assurance Lead:** Responsible for defining verification scenarios, ensuring coverage, and reviewing test reports.

## 6. Records
The objective evidence of verification activities will be maintained as QMS records per QMS-4.2.5-01. This includes:
*   Automated test reports generated by GitHub Actions.
*   CI/CD execution logs.
*   Approved Pull Request records demonstrating code review.
These records are maintained electronically and linked to the specific software version (Git tag) in the DHF (QMS-7.3.10-01).

## 7. Scope and Applicability
This verification plan applies to all unit tests, integration tests, static code analysis, and security verification performed on the Naomi codebase.

## 8. Terms and Definitions
*   **Verification:** Confirmation, through the provision of objective evidence, that specified requirements (Design Inputs) have been fulfilled by Design Outputs.
*   **Adversarial Testing:** Simulated cyber or prompt injection attacks designed to challenge software safety boundaries.
*   **Regression Testing:** Re-running test suites to ensure that software modifications have not introduced unintended defects.

## 9. Responsibilities Summary
*   **Lead Developer:** Writes unit/integration tests, ensures CI pipeline health, and reviews code.
*   **Quality Manager:** Confirms verification completeness against Design Inputs (QMS-7.3.3-01) and signs off verification reports.
*   **Clinical Safety Officer:** Validates clinical test scenarios and acceptable outcome criteria for triage classification.

## 10. Inputs and Outputs
*   **Inputs:** Design Inputs (QMS-7.3.3-01), Design Outputs (QMS-7.3.4-01), Risk Controls (QMS-14971-02), IEC 62304 verification requirements.
*   **Outputs:** Automated Vitest execution logs, GitHub Actions verification test reports, verified software build ready for validation (QMS-7.3.7-01).
